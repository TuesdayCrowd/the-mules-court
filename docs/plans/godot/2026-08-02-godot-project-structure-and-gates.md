## 1. Project layout

### 1.1 Same repo, not a sibling repo

`godot/` lives inside `the-mules-court`, alongside `src/`, not in a new repository. This is deliberate and it is the whole point of Stage 2 running in parallel with Stages 0–1 rather than after them: **same-repo CI is the only way to catch wire drift between two implementations while both exist.** A sibling repo means the TS engine's `protocol.ts` and the GDScript port's message-parsing can silently diverge for a week before anyone notices — no CI job spans two repos for free. One repo means a single Actions run can regenerate the conformance corpus from the TS engine (doc 3) and immediately fail the GDScript suite in the same job, on the same commit, before either side's author has left the PR. The retiring-oracle model (master plan §2, "replay and then retire") only works if the oracle and the replay sit where one CI graph can see both.

### 1.2 Directory shape

```
godot/
├── project.godot              # Godot 4.7.1 project file
├── export_presets.cfg         # committed — the export matrix (§6) lives here
├── .gitignore                 # ignores .godot/ only (§1.3)
├── engine/                    # Stage 3 — deterministic reducer (doc 4), rng.gd (doc 2)
├── ai/                        # Stage 6 — inference path only (doc 5): policy, heuristic, census, determinize, search, difficulty, rng
├── server/                    # Stage 4 — rooms, wire, persistence, seat tokens, dispatch (doc 6)
├── client/                    # Stage 5/7 — scenes, store, beats, the Mule SubViewport shader (doc 7)
├── assets/                    # Stage 2 — the existing PNGs, imported losslessly, never regenerated (doc 8)
├── test/                      # GUT specs (§3), mirrored per subsystem: test/engine, test/ai, test/server, test/client
│   └── vectors/                   # generated cross-language JSON (doc 2 Task 6, doc 3) — committed, regenerated by a script, never hand-edited
└── theme/                     # generated .theme resource + .gdshader files (doc 8)
```

Each top-level directory under `godot/` mirrors a `src/` directory 1:1 by *responsibility*, not by file count — `godot/engine/` is where `reduce()`'s GDScript twin lives, not a literal transliteration of `src/game/engine/`'s file list. `godot/test/` mirrors the subsystem split (§3.4) rather than sitting flat, for the same reason `src/server/__tests__/` sits beside `src/server/` rather than at the repo root.

**R1.1** Every top-level `godot/*` subsystem directory SHALL have a matching `godot/test/*` directory before that subsystem's Stage begins, and the CI invocation (§3.3) SHALL name it explicitly. This is not optional ceremony — it is the direct GDScript analogue of the asymmetry AGENTS.md already documents for the TS side: `vitest.config.ts` enumerates globs (so a new `src/` directory is type-checked automatically) while the two `bun test` scripts name directories by hand, which is why `test:mcp` had to be added explicitly when `src/mcp/` first appeared, and why nothing catches a forgotten one. GUT's `-gdir` flag (§3.3) is a **named-directory** invocation, structurally identical to the `bun test` half of that split, not the auto-discovering half — so the discipline is: **a new `godot/<subsystem>/` directory is silent and untested until someone edits the CI job.** Put a checklist line in whichever doc adds the directory (docs 4–8 each open a new one) rather than trusting anyone to remember.

### 1.3 Ignore `.godot/` only; commit `.import` sidecars

```gitignore
# godot/.gitignore
.godot/
```

`.godot/` is Godot's local cache (compiled shaders, editor scratch state, per-machine UID resolution cache) and is exactly analogous to `node_modules/` or `dist/` — regenerable, machine-specific, and large. **`.import` sidecar files are committed**, not ignored. Every imported asset (every PNG under `godot/assets/`) gets a sidecar `.import` file holding import settings and the resource's UID [verified: godot-docs issue #11875 and corroborating community sources]. Committing them is what makes a fresh clone reuse the same import settings and the same UIDs a teammate's machine produced, rather than re-deriving them — the Godot-side equivalent of committing `embeddedAssets.generated.ts` (AGENTS.md, "committed but generated," same reasoning: a clone without it fails the gate it's needed for). An ignored `.import` tree means every fresh clone re-imports every asset on first open, and if two contributors' re-imports produce different UIDs, a resource reference that looked stable in one clone silently points at the wrong file in another — a failure mode with no message and no stack trace, just wrong art on screen.

**R1.2** `godot/.gitignore` SHALL contain exactly `.godot/` and nothing broader. Do not add `*.import` to it under time pressure — that trade buys smaller diffs and pays for it in exactly the failure mode above.

### 1.4 `project.godot` and `export_presets.cfg`

Both are committed, ordinary Godot project files — `project.godot` at the `godot/` root (so `godot/` *is* the Godot project, not a subdirectory of one — no nested project-inside-repo layer), and `export_presets.cfg` alongside it, holding the preset definitions §6 exports from. Neither is generated; both are hand-authored and reviewed like source, because both encode decisions (autoload order, feature tags, per-preset signing config) that a stale or silently-regenerated copy would make wrong in a way that only shows up at export time.

## 2. GDScript conventions worth pinning

These are not a style guide. Each one exists because getting it wrong compiles, runs, and produces a wrong answer with no error — the exact failure class doc 2 spent 300 lines closing for the RNG. Pin them here so every later doc inherits the same defaults instead of re-deciding per file.

### 2.1 `int` is 64-bit signed — no `uint`, no `>>>`, no `Math.imul`

Confirmed: GDScript's `int` is "equivalent to `int64_t` in C++" [verified: gdscript_basics.html], with no unsigned type at all, and no `>>>` or `Math.imul` equivalent anywhere in the language [verified by absence — see doc 2 and the determinism research]. **Every 32-bit algorithm in this project masks every intermediate to `& 0xFFFFFFFF`, and every 32×32-bit multiply goes through the 16-bit-half `mul32_safe`, never a raw `a * b`.** Doc 2 is the canonical worked example (`Rng.mul32`, `Rng.seed_rng`, `Rng.next_rng`) — the naive `(a * b) & 0xFFFFFFFF` is not merely imprecise, it **overflows `int64`** at the top of the 32-bit range (`0xFFFFFFFF² ≈ 1.8×10^19` against an `int64` ceiling of `≈9.2×10^18`), so this is not a style preference, it is the difference between a working shuffle and a corrupted one that looks fine until a large seed hits it. Any new GDScript file touching a hash, a checksum, a packed bitfield, or anything else that was 32-bit-unsigned in TypeScript inherits this rule; do not re-derive it per file, cite doc 2 §"the hazard, in full."

### 2.2 Static typing on, everywhere

`var x: int`, not `var x`. Function signatures declare parameter and return types (`static func mul32(a: int, b: int) -> int`, as doc 2 already does throughout). This is not merely a lint preference: GDScript's static analysis catches a class of bug this project's TypeScript side gets from `strict: true` for free (AGENTS.md, "TypeScript gotchas") — an untyped GDScript function that returns a `Dictionary` in one branch and `null` in another compiles silently and fails at the call site, at runtime, in whatever context happened to hit that branch first. Every function this suite writes should read the way doc 2's `Rng` class already does.

### 2.3 `class_name` for every shared type

A type shared across `engine/`, `ai/`, `server/`, and `client/` — `RngState`-equivalent, a card-catalog entry, a `RedactedView` shape — gets a top-level `class_name` declaration (as `Rng` already does in doc 2) rather than being redefined per-consumer or passed as an untyped `Dictionary` everywhere it's used. `Dictionary` is still the right choice for genuinely JSON-shaped state (§2.4) — the distinction is between a *shape everyone must agree on* (gets a class) and *state whose shape a JSON wire message already pins* (stays a Dictionary, because a class would just be a parallel restatement of the wire).

### 2.4 `Dictionary` for JSON-shaped state

Engine state, `RedactedView`, and wire messages are `Dictionary` values keyed by string, mirroring the plain-JSON-object shape they have on the TS side and on the wire itself (master plan §6.1, §6.2; doc 3's corpus records these as canonical JSON precisely because both languages can round-trip a `Dictionary`/JS-object through the same JSON without a translation layer that could itself introduce drift). This is also why `RedactedView`'s redaction is a **diff obligation, not a type** (master plan §6.2) — a `Dictionary` has no compiler to forbid an extra key the way a TS discriminated union does, which is exactly what makes the corpus load-bearing rather than decorative.

### 2.5 `RefCounted` for cursors and services

A stateful-but-not-a-Node helper — the AI's `AiRng` cursor (doc 2 Task 5), a room's dispatch pipeline, a socket wrapper — extends `RefCounted`, not `Node` and not a bare `class_name` with static state. `RefCounted` gives automatic memory management with no scene-tree membership, which is the correct shape for something that is a *service* (constructed, used, discarded) rather than a *thing that exists in the world* (which is what `Node` is for). Doc 2's `AiRng` is the pattern: `class_name AiRng extends RefCounted`, one field, no `_ready`, no `_process`.

### 2.6 Autoloads for the store, socket, and server singletons

The client's single `ClientState` subscriber (AGENTS.md: "no surface reads the store; `update(state)` is pushed by a single subscriber"), the WebSocket connection, and (for offline solo, master plan §3.3) the in-process server each get exactly one autoload singleton — mirroring the TS side's composition root (`src/main.ts` constructs one store, one socket, wires them together) rather than letting any scene reach for global state ad hoc. An autoload is Godot's version of a singleton, and singletons are otherwise flagged as an anti-pattern in this project's own standards (`AGENTS.md`'s user-global CLAUDE.md: "Interfaces over singletons — enable testing and flexibility"). The resolution is the same one the TS side already uses: **exactly one** of each (store, socket, server-if-offline), constructed once at the equivalent of a composition root, injected into everything else — not scattered ambient global mutable state reached from arbitrary scenes. A second `ClientState` autoload, or a scene that reads `Store.state` directly instead of receiving it via `update(state)`, reintroduces the exact bug class §6.6 (master plan) rules out: "any GDScript that caches a derived game fact across frames is a bug."

### 2.7 No ambient randomness

Every random draw in `engine/` and `ai/` takes an explicit RNG state/cursor as a parameter and returns the advanced state — never `randi()`, `randf()`, or any bare global-RNG call. This is the GDScript mirror of the TS engine's own discipline (`RngState` passed and returned, never a module-level `Math.random()`), and it is what makes the corpus (doc 3) and the determinism proof (doc 2) possible at all: a hidden call to Godot's global RNG inside `engine/` would make two runs of the same seed diverge invisibly, and — per master plan §6.3 — the match RNG threads continuously across rounds and is never re-seeded, so a single stray ambient draw anywhere in a round's resolution silently desyncs every round after it. If a function in `engine/` or `ai/` needs randomness and doesn't have an `Rng`/`AiRng` parameter, that is the bug, not a missing feature.

## 3. The test framework decision (master plan gate 4)

### 3.1 GUT vs gdUnit4

Both frameworks support Godot 4.7.x:

| | GUT | gdUnit4 |
| --- | --- | --- |
| 4.7 support | Dedicated `godot_4_7` branch, tagged **v9.7.1** [verified: bitwes/Gut README version-compatibility table] | Master branch (v6.2.1) lists "v4.5 … v4.6.3, v4.7, v4.7.1" explicitly [verified: godot-gdunit-labs/gdUnit4 README compatibility table] |
| Headless CI invocation | `godot --headless -d -s addons/gut/gut_cmdln.gd -gdir=res://test -gexit` [verified: multiple independent CI-integration writeups corroborate the flag names; not fetched from bitwes/Gut's own docs site directly in this research pass] | `godot --headless --path "$PWD" -s -d addons/gdUnit4/bin/GdUnitCmdTool.gd -a ./test -rd ./test/reports --ignoreHeadlessMode` [verified: community pattern corroborated; exact syntax not independently confirmed against gdUnit4's own docs] |
| Nonzero exit on failure | `-gexit` is documented **specifically** to make GUT return a CI-usable nonzero exit code on any failure — this is a well-corroborated, mature pattern going back years across independent writeups | Markets itself as CI/CD-ready with structured JUnit XML report output; exact exit-code contract **not independently confirmed** in this research pass [uncertain] |

**Decision: GUT.** Two reasons, both about how much the gate can be trusted unattended:

1. **The `-gexit` → nonzero-exit-on-failure pattern is the better-corroborated of the two.** This project's entire character is gates that fail loudly (`AGENTS.md`: "this project's entire character is that it has gates"; master plan: "a Stage is done when its corpus assertions pass headless in CI — not when it looks right"). A CI gate that silently returns 0 on a failed assertion is worse than no gate — it is a green checkmark lying about the state of the code, exactly the failure mode `running-the-test-gates` exists to prevent on the TS side. GUT's exit-code contract is confirmed across multiple independent sources; gdUnit4's is plausible-but-unconfirmed. Given a choice between "well-corroborated" and "probably fine," pick well-corroborated for the thing every other gate in this plan depends on being trustworthy.
2. **GUT is the older, more battle-tested project**, with the `-gexit` CI pattern documented across years of independent community writeups rather than one framework's own marketing claim. gdUnit4's purpose-built CLI tool and JUnit XML output are genuinely nicer for report *consumption* (a CI dashboard that parses JUnit XML natively), but this project doesn't currently have a CI dashboard that consumes JUnit XML — it has GitHub Actions checking an exit code, exactly like `bun test` and `vitest run` already do. JUnit XML is a real advantage the day this project wants richer CI reporting; it is not a reason to trade away exit-code certainty today.

**R3.1** If gdUnit4's exit-code contract is later independently confirmed and this project acquires a reason to consume structured JUnit XML (a CI dashboard, a flaky-test tracker), revisit this decision explicitly rather than silently switching — a mixed GUT/gdUnit4 test tree is a worse outcome than either framework alone, for the same reason this repo has exactly two test runners on the TS side and documents precisely why the split exists rather than letting a third creep in.

### 3.2 Installing GUT — the licence boundary, restated

GUT is MIT-licensed [not independently re-verified in this research pass — confirm before installing] and is a normal `addons/gut/` dependency, not a code-reference situation — this is unrelated to the `GD-Agentic-Skills` LGPLv3 boundary (§7): GUT is a *test framework dependency*, installed and used as intended, not a source of code to copy into `godot/engine/` or `godot/client/`. Install it via the Asset Library or a git submodule/subtree into `godot/addons/gut/`, per its own installation instructions.

### 3.3 The exact headless command

```bash
godot --headless -s addons/gut/gut_cmdln.gd -gdir=res://test -gexit
```

- `--headless` forces the dummy display/audio driver, works on any 4.x binary from 4.0 onward, and requires no separate "server" build [verified: docs.godotengine.org dedicated-servers export docs].
- `-gdir=res://test` is the **named-directory** argument — per §1.2's `R1.1`, this must be updated (or split into per-subsystem invocations, §3.4) every time a new `godot/test/<subsystem>/` directory is added, or that subsystem's suite runs zero tests and reports success by omission.
- `-gexit` is the flag that turns a failed assertion into a nonzero process exit code, which is the entire CI contract — a CI job that runs GUT without `-gexit` will report green regardless of what the tests found, because GUT's default behavior (interactive-editor-friendly) is not to force an exit at all.

### 3.4 Per-subsystem invocation, matching the TS two-runner split

The TS side splits by *runtime* (Vitest under Node can't load `bun:sqlite`; `bun test` can), not by preference (AGENTS.md, "Testing instructions"). GDScript has one runtime, so there is no equivalent forced split — but the CI job still names each subsystem directory explicitly, both to keep `R1.1` honest and so a failure in `godot/test/server` is attributable at a glance rather than buried in one monolithic `res://test` run:

```bash
# CI: godot-test job, one line per subsystem, named explicitly (never a bare res://test)
godot --headless -s addons/gut/gut_cmdln.gd -gdir=res://test/engine -gexit
godot --headless -s addons/gut/gut_cmdln.gd -gdir=res://test/ai     -gexit
godot --headless -s addons/gut/gut_cmdln.gd -gdir=res://test/server -gexit
godot --headless -s addons/gut/gut_cmdln.gd -gdir=res://test/client -gexit
```

**R3.2** Adding a fifth `godot/<subsystem>/` (there is no plan to, but see doc 6 §1's noted alternative of keeping the Bun server) SHALL add a fifth line here in the same commit that adds the directory — not "in a follow-up," which is exactly how `src/mcp/` went untested on the TS side until `test:mcp` was added as a deliberate fix for an asymmetry that had already shipped.

## 4. Mirroring the verification gate

The TS project's definition of done is three commands (AGENTS.md, "Testing instructions"):

```bash
bun run test        # engine/client (Vitest) + server + MCP (bun test)
bunx tsc --noEmit    # the only type check — neither vite build nor dev server type-checks
bun run build        # confirm the production bundle still builds
```

The GDScript equivalent is also three commands, and the reasons they're three (not one, not two) carry over almost exactly:

### 4.1 The headless GUT run — mirrors `bun run test`

The four-line invocation in §3.4, run in CI as one job (`godot-test`). This is the behavioural gate: every corpus assertion (doc 3), every RNG stream/shuffle vector (doc 2), every server transport fact (doc 6 §"the risk," reconnection ordering, replay-is-determinism, the strict parser), every client purity/topology fact (doc 7) that has a GDScript-side test at all.

### 4.2 A parse-check — mirrors `bunx tsc --noEmit`

**This is the one genuine asymmetry, and it must be named as such rather than papered over.** TypeScript has a real, separate type-checker (`tsc --noEmit`) that catches a whole category of bug — a wrong field name, a missing case in a union match, an argument of the wrong shape — **before** any test runs, for free, on every file in the tree whether or not a test touches it. **GDScript has no separate typechecker.** Static typing (§2.2) is enforced by the same engine that runs the game, at parse/compile time when a script is loaded, not by an independent tool you can point at the whole tree.

The closest available substitute is forcing Godot to **load every script** without running the game, so a parse or type error surfaces as a nonzero exit rather than only being discovered the first time some code path happens to execute:

```bash
godot --headless --check-only godot/some_script.gd   # [uncertain] — verify against the 4.7.1 binary before relying on this in CI
```

**[uncertain]** — the exact flag is not confirmed by this project's research pass; the two candidates worth spiking before Stage 2's CI job is finalized are `--check-only` (a per-file parse/check flag referenced in older Godot CLI documentation) and a `--quit-after <n>` full-project load (open the project headless, let every autoload and referenced script get loaded and compiled, then quit after `n` frames without rendering). Either would catch "this script references an undefined `class_name`" or "this function signature doesn't match its declared return type" project-wide; neither has been independently verified against the actual 4.7.1 CLI in this research. **Spike this explicitly in Stage 2** (a two-line project with one deliberately broken script, confirm the chosen flag exits nonzero) before trusting it as a gate — the same one-to-two-hour spike discipline as master plan §11's numbered gates, just not numbered there because it's Stage 2 machinery rather than an architecture decision.

**R4.1** Whichever flag is confirmed, it SHALL run over the whole `godot/` tree (all four subsystem directories plus `godot/test/` itself), in CI, as a separate job from §4.1 — mirroring why `bunx tsc --noEmit` is a separate command from `bun run test` rather than folded into it: a parse/type failure and a behavioural-assertion failure are different classes of red, and collapsing them into one job loses the signal of which kind of broken the tree is.

### 4.3 An `--export-release` smoke build — mirrors `bun run build`

```bash
godot --headless --export-release "<preset-name>" /dev/null   # or a scratch path; confirms the export pipeline itself is not broken
```

[verified: `godot --headless --export-release "PresetName" path/to/output` is the standard headless CI export invocation — codemagic.io, deepwiki export-system-overview, corroborated across sources]. This does not need to run every preset in §6's matrix on every commit — one representative preset (pick the native desktop target the CI runner's OS matches) is enough to confirm the export pipeline itself hasn't broken, the same way `bun run build` confirms `vite build` produces a bundle without confirming every deployment target works. The full export matrix (§6) is a release-time job, not a per-commit one — mirroring how this repo's cross-compiles (`compile:linux-x64` and friends) are not part of the per-commit `bun run build` gate either.

### 4.4 Where each runs

| Gate | Mirrors | CI job | Cadence |
| --- | --- | --- | --- |
| §4.1 headless GUT | `bun run test` | `godot-test` | every commit/PR |
| §4.2 parse-check | `bunx tsc --noEmit` | `godot-check` | every commit/PR |

## 5. The corpus gate as a first-class CI job

Doc 3's conformance corpus is not a fixture checked in once and forgotten — it is **regenerated from the TS engine on every run** and the GDScript layers are asserted against the fresh output, in the same job, on the same commit. This is what makes it a *gate* rather than a snapshot:

```
godot-corpus job:
  1. bun run gen:corpus          # regenerate godot/test/vectors/*.json from src/game/engine (doc 3, doc 2 Task 6)
  2. git diff --exit-code godot/test/vectors/   # fail loudly if committed vectors are stale — R6.2/R6.3 (doc 2)
  3. godot --headless -s addons/gut/gut_cmdln.gd -gdir=res://test/engine -gexit   # replay every corpus match frame-for-frame
```

**A rule or protocol change reddens this job until every layer updates**, by construction: step 1 regenerates from whatever `src/game/engine/` currently says, step 2 fails if that regeneration doesn't match what's committed (catching "someone changed a rule and forgot to regenerate"), and step 3 fails if the GDScript engine doesn't reproduce the regenerated frames (catching "someone changed a rule in TS and the GDScript port hasn't caught up yet"). This is the direct CI encoding of master plan §6.1's closing sentence: "a change to the protocol is retroactive across every stored match and regenerates the corpus." A GDScript engine that silently drifts from the TS oracle during the migration window (master plan §2: "during the migration the two coexist, deliberately") is exactly the failure this job exists to make loud instead of quiet.

**R5.1** `godot-corpus` SHALL run on every PR touching any of: `src/game/engine/`, `godot/engine/`, `godot/test/vectors/`, or `scripts/gen-rng-vectors.ts`/the doc-3 corpus generator — not gated to a subset, because the whole point is that a change in *either* language shows up here.

## 6. Export matrix (Stage 8)

### 6.1 Command and preset requirements

```bash
godot --headless --export-release "<PresetName>" <output-path>
```

[verified: standard headless export invocation, multiple corroborating sources]. Presets are pre-configured in the editor and stored in `godot/export_presets.cfg`, which is committed (§1.4).

**Export templates must match the editor version exactly** — a version mismatch between the editor/CLI binary and installed export templates is a known CI failure mode [verified: general Godot export-docs pattern, corroborated across sources]. CI must install 4.7.1 templates matching the 4.7.1 binary the job runs, not "whatever templates happen to be cached."

### 6.2 Per-preset target list

| Preset | Platform | Notes |
| --- | --- | --- |
| macOS (arm64/universal) | Native | Requires macOS runner, Xcode CLT, env-var signing (§6.3) |
| Windows (x64) | Native | Signing specifics **[uncertain]** — not independently confirmed for 4.7 |
| Linux (x64) | Native | No signing requirement |
| Android | Native | Requires Android build template, JDK 17, Android SDK, keystore |
| iOS | Native | Signing specifics **[uncertain]** — standard Xcode-side codesign/provisioning almost certainly still applies, not independently confirmed for 4.7 |
| Web | Gated | Only built at all if master plan §11 gate 1 passes; otherwise this preset does not exist in `export_presets.cfg` |

This mirrors master plan §3.3's native-first commitment directly: five native presets are unconditional Stage 8 work, the Web preset is conditional on a gate that may simply say no.

### 6.3 Embed-PCK for single-file distribution

Godot's default release output is an executable plus a separate `.pck` data file; **"Embed PCK"** is an export-settings checkbox that folds the `.pck` into the executable, producing one self-contained binary [uncertain/post-cutoff — general Godot export behavior, stable across many versions, exact 4.7 checkbox wording not independently re-verified this pass]. This is the direct analogue of `bun run compile`'s single-file executable (AGENTS.md, "The single-file binary") and should be the default for every native preset in §6.2, for the same reason the Bun build defaults to it: a downloaded binary that runs from any directory with nothing else installed is the whole value of a native release.

### 6.4 Signing notes per platform

- **macOS:** requires the export step to actually run on macOS with Xcode command-line tools present; environment variables can override editor-configured signing/notarization settings, which is what lets CI sign without committing secrets to the repo [verified: strayspark.studio guide and Godot's own macOS export docs, cross-referenced].
- **Android:** requires the Android build template, JDK 17, Android SDK/command-line tools, and a keystore configured per-preset; APK (sideload) vs. AAB (Play Store) is a preset setting [verified: strayspark.studio guide].
- **Windows:** **[uncertain]** — Godot has historically supported Authenticode signing via `signtool` in export settings; not independently confirmed for 4.7.1 in this research pass. Spike before Stage 8 commits to a signed Windows release, or ship unsigned for v1.0 and flag it in the README the way the existing Bun binary's own security posture is presumably already documented.
- **iOS:** **[uncertain]** — standard Apple provisioning-profile/Xcode-side codesign requirements almost certainly still apply; not independently confirmed for 4.7.1.

### 6.5 `SHA256SUMS.txt` is not a Godot feature

```bash
shasum -a 256 dist-bin/mules-court-* > dist-bin/SHA256SUMS.txt
```

Godot's `--export-release` produces binaries; it does not produce checksums. This is ordinary shell tooling run over the export output *after* the fact [verified as a general fact, not Godot-specific], mirroring exactly how this repo's existing `compile:linux-x64`-style cross-compiles need a manual `shasum` step layered on top today. **Mirror the existing binary-release workflow** — whatever GitHub Actions job currently produces and attaches `SHA256SUMS.txt` for the Bun binaries is the template; the Godot release job differs only in which command produces the binaries, not in how the checksums get made or attached.

### 6.6 What `godot-release` does, end to end

```
1. Install 4.7.1 editor + matching export templates
```

## 8. Licence discipline (master plan §12, restated with the operational specifics)

`GD-Agentic-Skills` is **LGPLv3**; every project here is **UNLICENSE**. The two are incompatible for anything copied wholesale:

- **Reference only.** Install `GD-Agentic-Skills` into the agent's plugin directory — outside `godot/`, outside this repo's tree entirely — read its patterns, and write original GDScript inspired by what you learned. This is what the DIA loop's Ingestion step is for (master plan §12).
- **Never copy a file from it into `godot/`.** Doing so makes that one file LGPLv3 sitting inside an UNLICENSE repository, and makes this repo's licence statement false the moment it happens — not a theoretical risk, a factually incorrect claim about the repo's own licence the instant the file lands.
- **Do NOT install two specific skills from that pack, ever:** `godot-multiplayer-networking` and `godot-adapt-single-to-multiplayer`. These teach exactly the high-level `MultiplayerAPI`/`MultiplayerSynchronizer`/`MultiplayerSpawner` architecture that master plan §3.2 forbids for structural reasons (state-ownership inversion, RPC-authority semantics standing in for seat-token auth, a replication model this project's server-authoritative-reducer design does not use). Installing either is not just a licence risk, it is an active invitation to reach for the wrong architecture at 2am under deadline pressure — the skill would be *right there*, teaching the pattern this whole rewrite explicitly rejects. Leave them uninstalled.

**R8.1** Any PR that adds a `godot/` file whose provenance is "adapted from GD-Agentic-Skills" SHALL be rewritten from the pattern, not the file, before merge — this is a licence-correctness requirement, not a style preference, and it is the one place in this document where "good enough for now" is not an acceptable interim state.

## 9. The manual accessibility gate (master plan gate 2)

The DOM client's `axe.test.ts` runs axe-core over every mounted surface automatically, on every commit, with one documented exception (`color-contrast`, covered arithmetically instead — AGENTS.md, "Testing instructions"). **This does not transfer.** Godot 4.5+ ships AccessKit, exposing `accessibility_name`/`accessibility_description`/`accessibility_controls_nodes`/`accessibility_described_by_nodes`/`accessibility_labeled_by_nodes`/`accessibility_flow_to_nodes`/`accessibility_live` on every `Control` [verified: class_control.html] — but AccessKit is explicitly described by the Godot team as experimental, with screen-reader support for the Godot **editor** itself incomplete and "follow-ups in future updates" expected [verified: godotengine.org/releases/4.5/ release announcement]. There is no GDScript-side equivalent of axe-core that can walk a scene tree headless and assert every accessible name is present and correct the way `axe.test.ts` does today — no such tool was found in this research, and none is proposed here, because inventing one would be exactly the kind of guessed-ahead-of-need work §7 argues against.

**The replacement is a manual pass, not an automated one, and it is a release gate, not a per-commit check:**

- Doc 7 ports every existing `aria-label`/`aria-describedby` string onto the corresponding `accessibility_name`/`accessibility_description` property, scene by scene, as each scene is built (Stage 5–7).
- Before a release ships, **a person runs a VoiceOver (macOS/iOS) or TalkBack (Android) pass on real hardware** against the built client, navigating every surface a player can reach — menu, lobby, action sheet, quick reference, seat dossier, overlays, the table itself — and confirms every control announces something a blind player could act on.
- This gate belongs in the same release checklist §6.6's export matrix runs against, not in `godot-test`/`godot-check`/`godot-build-smoke` (§4.4) — it cannot be a CI job by construction, since it requires a human with a screen reader and real hardware, exactly as this project's existing device QA pass already does (AGENTS.md: "the real-device QA pass (Task 34), which needs hardware and a person").

**R9.1** No release SHALL ship without a dated record of who ran the VoiceOver/TalkBack pass, on what OS version, and what (if anything) failed to announce correctly — an unrecorded manual gate degrades into a gate nobody remembers running, which is a worse state than admitting automation doesn't cover this and naming the human step explicitly, which is what this section does.
